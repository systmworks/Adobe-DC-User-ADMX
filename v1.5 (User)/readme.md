# v1.5 (User) — Adobe DC ADMX/ADML for Intune (HKCU Preferences)

28 Jun 2026

This ADMX targets **HKCU user preferences** for Adobe Acrobat DC and Reader DC. It is designed to complement the existing HKLM-based ADMX files (x64/x86) and covers settings that are not already managed through lockable machine policies.

## What is new in v1.5

| Area | Change |
|------|--------|
| **WS2019 GPMC compatibility** | ADML no longer includes an empty `presentationTable`, fixing Group Policy Management Console import failures on Windows Server 2019 reported when using v1.4. |
| **Revision** | ADMX `revision`, ADML `revision`, and `<resources minRequiredRevision>` are all **1.5** (aligned bundle version for Group Policy and Intune, same pattern as HKLM Adobe ADMX). |
| **Policy inventory** | Unchanged from v1.4 for this release: **484** policies (**250** Acrobat DC + **234** Reader DC), built from the same curated HKCU preference source and filtering rules. |
| **Documentation** | Published Markdown guides reference **v1.5** and are updated with this release. |

**Compared to the v1.4 template bundle:** namespace (`Adobe.Policies.Adobe_User`), category layout, and policy list are unchanged. The v1.4 bundle remains available for existing deployments that do not require the WS2019 GPMC fix. See the **v1.4 (User)** readme for the full v1.3 → v1.4 change list.

## Source data

Settings were sourced from the Adobe Preference Reference documentation:

- <https://www.adobe.com/devnet-docs/acrobatetk/tools/PrefRef/Windows/>

Only HKCU-specific settings are included. Any setting that already has a lockable HKLM policy (covered by the HKLM ADMX) was excluded to avoid duplication.

The publisher-maintained **HKCU preference** table for this project is the authoritative source for registry paths, DWORD mappings, STIG references, and optional **GoodSetting** suggestions. Published documentation is updated with each template release to match.

Each DWORD toggle policy maps Group Policy **Enabled** and **Disabled** to explicit registry DWORD values (the same pattern as the HKLM ADMX in v2.15). A small number of policies include optional recommended-security notes and DISA STIG cross-references in their description text.

## Filtering (unchanged)

The following categories of settings were excluded:

- **HKLM duplicates** — settings already covered by the lockable HKLM ADMX (53 entries).
- **Application-managed** — read-only values generated by the application at runtime (e.g. subscription/license state).
- **Pre-DC versions** — settings whose version range indicates they do not apply to DC (e.g. `7.0-8.0`, `9.0-10.0`).
- **Template/placeholder paths** — settings with registry paths containing placeholders like `c{n}`, `c[someExtension]`, or `(version)` that represent per-instance keys rather than concrete policy targets.
- **Malformed paths** — entries with embedded `HKLM\` fragments or forward slashes in the HKCU path.
- **Non-DWORD types** — only REG_DWORD settings are emitted as ADMX toggle policies. REG_SZ, REG_BINARY, and other types are not represented as simple toggles in the ADMX.

## Known issues

- **`class="Both"`**: Intune does not support `class="User"` for custom ADMX ingestion. All policies use `class="Both"` as a workaround. When assigned to a **user group** in Intune, the settings write to HKCU as intended. When assigned to a device group, they write to HKLM at the same path — which is not the intended use for these preference settings.
- **Skipped (unresolvable paths)**: The source table does not include DWORD entries whose HKCU paths still contain placeholders such as `c{n}`, `c[someExtension]`, or `(version)`; those settings are omitted from this ADMX. **`ADC4318556`** (Flash Player for 3D) is included when paths are concrete. **Open in Acrobat** and similar keys with unresolvable paths were dropped from the source and do not appear here.
- **Non-DWORD types excluded**: **46** `REG_SZ` reference entries remain in the source data for documentation alignment; they are not emitted as ADMX toggle policies. `REG_BINARY` and other non-DWORD types would require different ADMX elements.
- **No Cloud & Connectors category**: AVEntitlement-related settings (licensing/subscription status) were excluded as application-managed, so this bundle does not define that category for Acrobat or Reader.

## Intune upload

1. Remove any existing ADMX entry for the `Adobe.Policies.Adobe_User` namespace before uploading, or Intune will report a conflict.
2. Upload `AdobeDC_User.admx` and `en-US/AdobeDC_User.adml` together.
3. The HKLM ADMX files use a separate namespace (`Adobe.Policies.AdobeDC`) and do not need to be removed.
4. Assign the resulting policy to a **user group** to write settings to HKCU.
5. If upload returns a generic **Command error, check your command query...**, remove any failed import for this namespace, confirm the ADML file is ASCII-only and within Intune's size limit, and retry uploading both ADMX and ADML together. Revision alignment alone is not usually the fix for this error.
